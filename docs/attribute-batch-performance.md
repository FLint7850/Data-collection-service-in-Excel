# Большие обработки атрибутов

При открытии обработки интерфейс получает её метаданные и первую страницу из 80 товаров. В списке передаются только ID, модель, название, бренд, статус и счётчики. Характеристики и источники загружаются отдельно после выбора товара. Поиск и фильтры выполняются на сервере по всей обработке; переход между страницами сохраняет открытый товар. Прямая ссылка на товар загружает только его детали.

## API

- `GET /api/attribute-assistant/batches/<id>` возвращает метаданные и сводку без массива товаров.
- `GET /api/attribute-assistant/batches/<id>/products?q=&status=all&offset=0&limit=80` возвращает `items`, `total`, `matched`, `offset`, `limit`, `has_more` и общие счётчики фильтров `counts`. Размер страницы ограничен 200 строками. Поиск учитывает модель, название и бренд, включая регистр русского текста.
- `GET /api/attribute-assistant/products/<id>` возвращает характеристики и источники выбранного товара.
- Импорт и массовые действия возвращают метаданные обработки; интерфейс затем обновляет текущую страницу списка.

Лимиты страниц больше не разбросаны по маршрутам и интерфейсу. Backend хранит стабильные параметры поведения модуля в `services/attribute_settings.py`, а `GET /api/attribute-assistant` возвращает нужную клиенту часть в секции `settings`. Запоздавшие запросы списка, карточки товара, шаблона и справочника отменяются через `AbortSignal`, а не только игнорируются после получения ответа.

Изменяющие товар endpoints возвращают единый mutation-контекст: изменённый товар или значение, свежие метаданные обработки и историю товара. Поэтому ручное принятие значения больше не вызывает следом отдельные запросы обработки, страницы товаров и истории.

Список и сводка используют SQL-агрегации и не создают объекты товаров и их значений в ORM. При изменении значения обновляются выбранный товар и сводка, без обхода остальных товаров. Запрос списка без поиска выполняет два SQL-запроса; поиск добавляет запрос числа совпадений. Счётчики отражают актуальные сохранённые данные, без долговременного кеша.

Поиск по разрешённым значениям и синонимам также выполняется в SQL. В ORM загружается только запрошенная страница; редактор шаблона умеет последовательно догружать следующие страницы вместо скрытого ограничения первыми 80 значениями.

## Импорт и экспорт

CSV импортируется блоками по 100 товаров: после записи блока объекты товаров и значений освобождаются из сессии. Весь импорт остаётся одной транзакцией, поэтому ошибка не сохраняет частично созданную обработку. Повторные сочетания поля, исходного значения и названия атрибута сопоставляются один раз за импорт. Этот кеш не переживает импорт и не мешает обновлению справочников или синонимов.

Экспорт последовательно читает скалярные строки из базы и записывает CSV. В память не загружается коллекция товаров обработки. Экспорт всех товаров охватывает всю обработку независимо от открытой страницы; экспорт готовых использует сохранённый статус товара. Формат остаётся `_MODEL_;_ATTRIBUTES_`, кодировка CP1251.

При запуске backend автоматически создаются индексы `attribute_products(batch_id, sort_order, id)` и `attribute_product_values(product_id)` для существующей базы. Обновление идемпотентно. Для применения изменений нужны обновлённый backend и пересобранный либо перезапущенный frontend.

Массовая проверка доноров обрабатывает несколько товаров параллельно, но не превышает меньший из `DONOR_PRODUCT_CONCURRENCY` и числа разрешённых вкладок донора. У каждого worker своя SQLAlchemy-сессия; браузерный диспетчер остаётся общим и синхронизированным. В очереди одновременно находятся только задачи по числу worker-ов, поэтому размер пакета не увеличивает расход памяти на объекты `Future`.

## Настройка

Стабильные параметры поведения модуля — размеры страниц, глубина истории, порог массового принятия, параллелизм доноров и лимит сохранённых ошибок — собраны в типизированном `services/attribute_settings.py`. Они намеренно не вынесены в `.env`: это не секреты и не deployment-настройки. В `.env` остаются только действительно внешние параметры вроде путей, сетевых лимитов и интеграции ChatGPT. UI-тайминги debounce/polling собраны в `frontend/app/config/attribute-assistant.ts`.

## Проверка

На 8 октября 2026 года последние обработки №4 и №5 содержали по 4898 товаров и 153315 значений атрибутов. В чтении обработки №5 список из 80 товаров сформировался примерно за 0,36 секунды; сериализация JSON в UTF-8 без ASCII-экранирования составила 17714 байт. Это замер сервиса на локальной базе без сетевой передачи и отрисовки браузером. Объекты товаров и значений при чтении списка не создавались. Сводка, вычисленная SQL, совпала с сохранённой.

Повторный импорт исходного CSV обработки №5 в отдельную временную базу с копией её справочника занял около 23 секунд. Импорт сохранил все 4898 товаров, а его сводка полностью совпала с исходной: 808 готовых, 4090 требующих проверки, 38457 заполненных и 15421 пустое поле, 3 конфликта, 91 предложение. Сопоставление значений вызвалось 461 раз благодаря кешу повторов. На границе записи блока в сессии находилось максимум 4450 объектов товаров и их значений вместо всей обработки. Рабочая база во время замеров открывалась только для чтения. Сравнение времени со старым алгоритмом не проводилось.

Автоматические проверки используют отдельную базу с 4000 товарами и проверяют:

- полноту импорта и экспорта, ограничение числа объектов при импорте и откат после ошибки в следующем блоке;
- страницы без повторов, русский поиск за пределами первой страницы и общие счётчики фильтров;
- загрузку метаданных и экспорт при запрещённой ленивой загрузке коллекции товаров;
- изменение одного товара без загрузки соседних и обновление сводки;
- добавление индексов в существующую схему при повторных миграциях;
- загрузку деталей по клику, прямые ссылки, задержку поиска и отклонение запоздавших ответов.
